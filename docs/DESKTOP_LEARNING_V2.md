# Windows V2: практика и проверяемые границы

Встроенная подготовка для всех 20 Python/PyTorch задач находится в `data/exercise_teaching.json`. Она написана отдельно для каждого фактического контракта: цель, развёрнутые предпосылки, шаги и API, разобранный пример на других данных, точное задание, ошибки и вопрос для объяснения. В интерфейс её передаёт `public_exercises()`. Исходник авторинга — `tools/write_desktop_teaching.py`.

Необходимые определения находятся внутри игры. Объясняются функции и return, методы/self, словари, множества, tensor shapes, autograd, nn.Module, train/validation/test, loss и optimizer. Внешние источники — углубление, а не скрытая предпосылка решения. Notebook `notebooks/practice.ipynb`, пересобираемый `tools/build_practice_notebook.py`, содержит те же 20 объяснений, starter-функции и самостоятельные проверки; среда notebook может потребовать установки PyTorch.

## Настоящий опыт с Dropout

В m19/exercise `normalization` учащийся собирает `Linear(2,16) → ReLU → Dropout(p) → Linear(16,1)` и пишет измерение MSE с `eval()` и `no_grad()`. Готовая LayerNorm показана отдельно, чтобы не смешивать нормализацию и регуляризацию.

Проверка действительно обучает созданные учащимся сети при p=0, 0.2 и 0.8. Для сравнения фиксируются разбиение, начальные веса, SGD lr=0.08 и 40 шагов. Шесть кривых содержат по 41 настоящему измерению: нулевой шаг и 40 обновлений. Train и validation измеряются в eval. Небольшие синтетические данные не дают универсального вывода о лучшем p. Перенос использует другой seed; выбранная архитектура и процедура остаются теми же.

Другие реальные PyTorch задачи включают autograd, зарегистрированные параметры, loss, очистку накопленных gradients, обучение линейной модели без validation leakage и scaled attention с сохранённым графом.

## Подключаемый агент

`model_adapter.run_local_agent()` вызывает указанный пользователем локальный HTTP API формата OpenAI chat completions. Модель возвращает JSON-действие; программа проверяет имя и аргументы, вызывает разрешённый игровой инструмент и передаёт фактическое наблюдение в следующий запрос. Бюджет — 1–4 ответа модели. Неизвестные действия, неверный JSON, ошибка API и исчерпание бюджета явно завершают попытку. Для открытия ворот требуется реальный результат предыдущего чтения датчика в этом же цикле.

Инструменты детерминированы и действуют только в вымышленном игровом мире. Сам агентный цикл не подменяет недоступную модель ответом-заглушкой. Обязательные офлайн-задания доступны отдельно и обозначены как детерминированные. Игра не скачивает веса. Подключённый пользовательский runtime может требовать заранее установленной модели. `success` в ответе означает штатное завершение протокола; содержательная верность ответа проверяется отдельно.

## Выполненные проверки, 16 ноября 2026

- `tests/test_exercises.py`: 13 тестов прошли с PyTorch 2.8 CPU. Все 20 эталонов проверены на обычных и переносных входах, включая самостоятельный notebook harness. Ошибочные starter-коды не получают завершение.
- `tests/test_desktop_exercise_teaching.py`: 5 тестов прошли. Все 20 разобранных кодовых примеров исполняются. Проверены одинаковый старт опыта, воспроизводимость, другой seed при переносе, изменение кривых при изменении весов учащегося, отбраковка отсутствующего Dropout и неверных eval/no_grad.
- `tests/test_local_agent_v2.py`: 6 тестов прошли через настоящий loopback HTTP с тестовым сервером. Проверены протокол, обратная передача наблюдений, бюджет, отказ от неразрешённых действий и обязательное чтение сигнала. Этот сервер является фикстурой, а не LLM: тест не доказывает реальный inference загруженной модели.

Проверки выполнялись в Linux. Они не подтверждают нативный запуск на Windows, качество конкретной внешней LLM или учебный эффект на человеке. Общий отчёт UI/сборки ведётся отдельно в `TEST_REPORT.md`. Содержание 40 концептуальных миссий и его аудит описаны отдельно в `MISSION_TEACHING_V2.md`.
