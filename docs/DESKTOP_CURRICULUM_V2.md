# Ручной аудит учебного содержания Windows V2

Дата: 16 ноября 2026. Объект проверки: 40 миссий `data/curriculum.json`, версия педагогики 2. Все миссии переписаны: 168 смысловых шагов, явные предпосылки, разобранный пример, связь с действием, разбор типичных ошибок и связь с Research Engineer интервью. Карта содержит 128 тематических записей; количество записей не является количеством независимо освоенных навыков.

Главный критерий аудита: чтобы выполнить задание, читатель не должен угадывать новое определение, API или предпосылку, отсутствующие в материале перед ним. Миссия объясняет концепцию и эксперимент; отдельный учебник упражнения объясняет конкретный Python/PyTorch интерфейс. Оба доступны из практики. Для восстановления контекста старое поле `lesson` также полностью обновлено, а не оставлено со старой теорией.

Исходный уровень учтён через явные определения функций, возвращаемого результата, словарей, индексов, `self`, наследования и инвариантов. Встреча с темой ранее не считается владением. Художественная сцена задаёт назначение действия, но не заменяет технический контракт метафорой.

## Десять сложных миссий: теория → действие → перенос

| Миссия | Что нужно уметь до действия | Где это объяснено | Как отличается пример от задания | Проверка и граница вывода |
|---|---|---|---|---|
| m03: порог | Определить positive class; TP/FP/FN/TN; выбрать знаменатель precision/recall; включить равенство в `score >= threshold`; соблюдать два ограничения одновременно | m03-s1–s4, предварительный разбор доли | В разборе 3 положительных и 2 отрицательных scores, в стенде 5 и 5; метод переносится на другую выборку и ограничения | FP — ложная тревога на безопасном случае. При смене positive class меняется смысл ячеек. Не обещается монотонность precision или калибровка score |
| m05: роли ML | Различить модель, прогноз, loss, optimizer и регуляризацию; понять L1/L2 и линейность по параметрам | m05-s1–s5 | Разбор `y_hat=w*x`, квадрат ошибки и λw² разделяет три величины. Карточки требуют отнести уже объяснённые операции к ролям | Добавление x² не отменяет линейность по весам. Улучшение validation при росте штрафа — результат конкретного опыта, а не универсальное правило |
| m09: данные и честный pipeline | K-Means/DBSCAN/PCA; значение variance; различие fit/transform; заполнение пропусков внутри train-fold; CV и подбор | m09-s1–s5; m02 напоминается в последовательности | Объясняется отдельное вычисление статистик; карточки проверяют процедурные действия и свойства методов | 95% variance не означает 95% качества по target. Fit imputer на всех данных до CV раскрывает информацию validation. Пропуск не считается нулём без основания |
| m15: loss | Формат MSE, logits и целые индексы CrossEntropyLoss; почему не нужен предварительный softmax; постановка positive/negative пар | m15-s1–s5 + учебник `losses` | Числовой MSE разбирается до выбора функции по `kind`; contrastive пример — отдельное объяснение, не скрытое требование написать отсутствующий API | Проверка logits/indices напрямую опирается на s2. Перенос к embeddings использует определение пар в s4. Выбор loss не доказывает качество разметки |
| m19: реальный Dropout | Linear/ReLU/Sequential, BatchNorm против LayerNorm, вероятность маски и масштаб 1/(1−p), независимость train/eval от no_grad, float MSE | Предпосылки, m19-s1–s5 + полный учебник `normalization` | Маска `[2,4,6,8] → [4,0,12,0]` — один возможный исход при p=.5; эксперимент использует p=0/.2/.8, реальные сети и историю ошибок | Стенд обучает три сети при одинаковых split/инициализации. `evaluate_mse` оставляет eval; перед следующим шагом нужен train. Исправность процедуры не зависит от обязательной победы выбранного p |
| m22: внимание | Скалярное произведение, деление на sqrt(d_k), softmax, взвешенная сумма, роли Q/K/V и маски | Предпосылки, m22-s1–s4 | В разборе Q=[0,1] и два keys; на стенде Q=[1,0] и три keys. Отдельный пример scores [0,ln3] даёт [.25,.75] | При тех же Q/K/маске изменение V не меняет веса. Максимальный вес не превращает смесь в hard selection. Веса не выдаются за доказательство истины |
| m28: вызов tools | JSON против schema; предложение против исполнения; проверка доступа; реальный tool result; точные аргументы учебных функций | m28-s1–s4 | Разбор разрешённого `canal` и неразрешённого `private` учит порядку проверок, а действие собирает причинную цепочку и позволяет вызвать локальную функцию | Валидная строка ID не означает право чтения. `set_gate` считает результат на учебных данных; это не управление внешними воротами. Текст JSON ещё не является выполнением |
| m31: ограниченный цикл | Переданная функция, while, словарь observation, позиция и направление, отдельный бюджет попыток | m31-s1–s4 + учебник `agent_loop` | Разбор start=4,target=2 содержит неподвижный промежуточный tool result; код проверяется на иных целях, бюджетах и наблюдениях | Счётчик растёт даже без движения. Текущее состояние берётся из результата, не из желания. При start=target нет вызова. Офлайн test double явно не называется настоящей LLM |
| m32: локальная модель и агент | Файлы → runtime → HTTP API → проверенное действие; JSON-протокол; наблюдение перед открытием; budget/stop | m32-s1–s5 | Разбирается connection refused, затем read_gate/open_gate с фактическим сигналом; пользователь может проверить свой runtime или пройти офлайн | Один ответ подтверждает только путь запроса. Бюджет 1–4; API/JSON/tool ошибки останавливают запуск. Success означает штатный протокол, а не истинность ответа или удостоверенную марку весов |
| m40: sliding window | Непрерывная подстрока, last-seen dict, индексы, длина right−left+1, left=max(left,last+1), монотонность границы | Предпосылки, m40-s1–s4 + учебник `longest_unique` | Разбор `cddc` пошаговый; проверка использует `abba`, код — несколько других структур и Unicode | Давний повтор вне окна не двигает left назад. Пустой вход даёт 0. Python str рассматривается по code points, без обещания поддержки grapheme clusters как одной буквы |

## Дополнительная проверка остальных частей

- m01–m02: задача отделена от режима обучения; происхождение меток и группы разделения объясняются до карточек. Риски многократной настройки validation проговорены, а test остаётся отдельным.
- m06–m08: bootstrap, разнообразие ошибок, sequential boosting, margin/C, kernel, условная независимость, масштаб, bias/variance и L2 имеют собственные определения и примеры. Старый факт о случайном split не требует заранее освоенной CV: краткое объяснение CV дано уже в m06.
- m10: прежний отвлечённый вопрос о максимуме отрицательного массива заменён на условие этой же задачи — почему нельзя сортировать цены и продавать раньше покупки.
- m11–m18: формы, dtype/device, broadcast, transpose/reshape, leaf/grad, module/forward, очистка градиентов и оценка разобраны последовательно. Учебные функции возвращают результаты в явно указанном формате. Образец отчёта m18 не утверждает, что игрок уже проверил несколько seeds.
- m21, m23–m26: tokens/vocabulary/context, causal mask, pretraining/SFT/RLHF/DPO, sampling, prefill/decode/cache не заменяются синонимами. Top-p считается по накопленной вероятности; softmax-стенд явно не назван реальной генерацией текста.
- m27, m29–m30: текст источника отделён от инструкции, ссылка — от доказательства утверждения, процедура — от намерения. Разбираются неизвестные ответы и конфликт дат/версий. Документ о метрике поддерживает вывод о критерии оценки, но не автоматически доказывает личный мотив.
- m33–m37: workflow/agent/MCP, LoRA/QLoRA/RAG, SFT/template/quantization/GGUF/distillation, judge и serving объясняются на разных уровнях системы. Обучение большой модели и запуск vLLM не приписываются карточной практике. Добавлены MLOps/LLMOps версии, мониторинг, rollback и различие KV/prefix/response/semantic caching.
- m38–m39: для стека сформулирован инвариант, а для исследования — baseline, ablation, пределы причинного вывода, reward proxy, value learning, corrigibility и мультимодальная связка восприятие → действие. Короткие английские фразы даны с переводом; сложный английский не используется как скрытая проверка знания ML.

## Проверки и пределы проверки

`python -m unittest discover -s tests -p 'test_*curriculum*.py' -v`: 14 тестов прошли. Шесть сохранённых проверяют маршрут, бюджет, источники, корректность интерактивных данных и карту тем; восемь новых проверяют completeness teaching, связи каждого действия/вопроса с существующим объяснением, доступность отдельного API-учебника, сложные учебные зависимости, числовые примеры attention/top-p/LoRA и честное разграничение офлайн/HTTP режимов. Проверка NPC исправлена с бессмысленного `len(name)>3` на явный набор Лейла/Сафар/Нур.

Это проверка учебного контракта и математической согласованности примеров. Автоматические тесты не доказывают педагогическую эффективность, а ручной аудит разработчика не заменяет прохождение независимым учащимся. Реальные PyTorch/reference/negative tests и протокольные tests описаны отдельно в `DESKTOP_LEARNING_V2.md`; браузерное прохождение и платформенные ограничения — в отчётах интеграции.
